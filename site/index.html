01 / the trade

Same browser. A better boundary.

The naming authority belongs on the machine with the browser, not inside every project. testd moves DNS, TLS, and registration to one place, then gets out of the way.

Without testd

  • A hosts edit, a vhost, and a certificate for every project
  • Self-signed warnings, or a browser flag you learn to ignore
  • Port forwarding that only works inside one IDE
  • A public tunnel opened just to look at a page on your phone

With testd

  • One fixed TLD, resolved by the host for every name you register
  • Leaf certificates minted on demand, valid for 24 hours
  • Names that exist only while the process that created them runs
  • Nothing reachable from the internet unless you ask for a share

02 / first name

Three commands, then the name is live.

Names are <service>.<project>. The host appends the TLD.

  1. 01

    Prepare the host

    Creates ~/.config/testd/config.toml, a local CA, and an operator secret. Resolver configuration and root trust wait for the first remote registration, or run doctor --fix now. 

    testd init
testd host
  2. 02

    Register a name

    The leaf asks the host for access. Approve it on the host with testd approve <id> or from the local dashboard. The token is saved and reused. 

    testd run app.example:3000 -- npm run dev
  3. 03

    Open the name

    The host resolves the name, terminates TLS, and proxies to the dev environment. Closing the terminal removes the name; the next run registers it again.

    Open https://app.example.test

03 / the model

One authority.
One connection.
No mesh.

The host owns DNS, TLS, the registry, and approvals. A leaf holds one outbound TCP connection and registers names on it. The browser never connects to the leaf.

  • The connection is the lease; a crash or lost network releases the name.
  • Tokens are durable permission, scoped to exact names and revocable.
  • There is no central service, account system, or cross-host mesh.

04 / operations

Built for the unglamorous parts.

Approvals, revocation, sharing, repair, and the desktop surface are part of the product, not an afterthought.

01

Access requests and tokens

A new machine asks for a grant. Approve it once; the token covers exact names and can be revoked without touching the operator secret or any other leaf.

02

Shares and tunnels

Reach a name from a phone, a webhook, or a colleague with cloudflared, ngrok, or a tailnet. The daemon owns the tunnel, so closing the terminal does not close the share.

03

Quick launches

Save a command in the dashboard or the tray. testd starts it, detects the listening port, and registers the name only after the target accepts.

04

Doctor and repair

One command checks configuration, the resolver, PKI, trust, and the edge. Exit codes are stable, and --json is meant for scripts.

05

Tray and notifications

Run the daemon, open the dashboard, approve requests, and start launches from the menu. Repair notifications carry an action, not just a warning.

06

External fronts

Already run Caddy or another front? Keep it. testd export-caddyfile writes the managed config, and the built-in edge is optional.

05 / trust

Small trust surface.

testd is a development tool, not a public ingress controller. It gives names and HTTPS to machines you control and keeps the authority local.

Read the security model →
  • The root key stays on the host. The root is installed once per browser machine. Leaf certificates live 24 hours and are minted on demand.
  • Issued tokens are scoped and revocable. The operator secret is bootstrap only. A leaked issued token can publish only its granted names.
  • Registration traffic is plain TCP. Use a trusted LAN, a VPN, or another encrypted transport. Do not expose intake port 7737 to the internet.
  • No account, no telemetry, no public dependency. No public DNS, ACME, or vendor API in the product. Tunnel providers are spawned processes, never linked SDKs.

A token is the key, its grants are the doors it may open, and a claim is a door currently held open.

06 / install

Up in three commands.

Build from source, use the install script, or install through Homebrew. The tray app is a separate Tauri build; the CLI works on its own.

  • macOS, Linux, and Windows
  • Public releases carry SHA256SUMS
  • No in-app updater or commercial service
